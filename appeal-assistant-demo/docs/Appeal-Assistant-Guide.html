Denied-Claim Appeal Assistant - Project Guide

Folder appeal-assistant-demo/ · Spring MVC 7 (no Spring Boot) + LangChain4j + Claude · Tomcat 11 in Docker · all data synthetic

1.Overview

In simple words: after a visit, a medical practice bills the patient's insurer (a claim). Sometimes the insurer refuses to pay (a denial) and gives a reason code. The practice can ask the insurer to reconsider (an appeal) by sending a letter plus proof from the chart. This demo lets AI prepare that letter and proof; a biller reviews, edits and approves it. Nothing is sent without that approval.

It is a working demonstration of one complete AI workflow with human approval, built the way it would be built inside an existing Spring MVC product: routing, tools, a check-and-fix loop, background processing, an approval screen and an audit trail.

5.How it works (flows)

5.1 Start-up

Tomcat finds WebAppInitializer (no web.xml), which starts Spring with WebConfig. Spring creates ClaudeModel (reads ANTHROPIC_API_KEY; without it the app still starts and shows a clear message), DemoData, AppealWorkflow, AppealService (with a pool of 4 background threads) and AppealController.

5.2 Preparing an appeal (request flow)

  1. The biller clicks Prepare with AI → POST /claims/{id}/prepare.
  2. AppealService.prepare() (synchronized - a double-click cannot start two paid runs) creates an Appeal with status PREPARING, copies any earlier audit history, logs the request and hands the work to a background thread.
  3. The browser is redirected to /appeals/{id}, which refreshes every 3 seconds while PREPARING. Tool reads appear live in the audit log.
  4. The background thread runs AppealWorkflow.run() (section 5.3), then stores the result and sets the review status.

5.3 The AI workflow (flowchart)

One path runs per claim. The checker always compares with the source records read by code, never with an AI-written summary.

5.4 Why the checker uses source records

If the checker compared the letter with the AI's own evidence summary, a fact the AI invented could "check itself" and pass. So ClaimTools.sourceRecords() - plain Java, no AI - builds the claim, chart, policy and authorization text, and every check (appeal letter, "not recommended" note and corrected-claim suggestion) is made against that.

5.5 Human review and the end of the flow

The review screen shows the claim and the collected proof on the left, the editable draft on the right, any remaining checker doubts as a warning, and the audit log. Approve stores the (possibly edited) text and marks the appeal "sent (simulated)"; Reject needs a reason and allows "Prepare again", which keeps the full audit history.

5.6 Errors

Any exception in the background run sets status FAILED with a readable message (never "null"); a finally block guarantees nothing stays in PREPARING. Approving something not under review answers 409, empty text or reason 400, an unknown claim 404.

6.ER diagram (data model)

The demo keeps its data in memory (Java records and maps) - there is no database. The diagram is the logical model, i.e. the tables this would become in SQL Server in a real product (section 7 lists the fields).

11.Statuses & audit log

The three middle statuses are "needs review". APPROVED is final - preparing it again is refused (409).

Audit log entries (actor · action): "biller.demo · Requested AI preparation", "AI workflow · Started", "AI workflow · Read (tool): chart entries" (live, one per tool call), "AI workflow · Finished: CATEGORY -> status (N agent steps, all statements checked)", "biller.demo · Approved with edits - sent to insurer (simulated)", "biller.demo · Rejected: reason". The log only grows - it is copied forward when an appeal is prepared again.

14.Build & deployment

Only Docker is needed on the machine - no Java, no Maven. The multi-stage Dockerfile builds the WAR with Maven 3.10.0 / JDK 21 and copies it into Tomcat 11.0.27.

On any machine with Docker Desktop

git clone https://github.com/SPM-Technologies/Agentic_AI_Workflows.git
cd Agentic_AI_Workflows\appeal-assistant-demo
# API key for this terminal only (hidden, not saved):
$env:ANTHROPIC_API_KEY = [Net.NetworkCredential]::new('', (Read-Host 'API key' -AsSecureString)).Password
docker compose up -d --build
# open http://localhost:8090/

Day to day

Maven's downloads are kept in a Docker build cache, so rebuilds after the first one are fast. A host build (mvn package with a local or Docker-based Maven) still works and produces target/ROOT.war, but is no longer needed.

16.Security, guardrails & known limitations

Guardrails built in

  • Human approval - nothing is "sent" without a biller's Approve; the biller can edit first.
  • Minimum necessary data - tools are bound to one claim's patient and take no patient id from the AI.
  • Checked against the system's own data - every draft is verified against source records read by code.
  • Coding compliance - the corrected-claim agent is told never to suggest higher-paying codes.
  • Full audit trail - AI steps, every tool read (live) and every human decision; never wiped.
  • Output escaping - all AI and user text goes through <c:out>.
  • API key - only in the terminal session and the container environment; never in files or images.
  • Cookie-only sessions - no session id in URLs.

17.Cost

Claude Opus 5.5 list price: $4 per million input tokens, $20 per million output tokens (October 2026). A claim uses 4-11 Claude calls: each step is one call, each tool round trip is one more, and every check / revise round adds two. Estimate: a few cents to about $0.50 per claim. Each click on "Prepare with AI" spends money - the double-click guard prevents accidental duplicates. Testing with the fake server is free.
